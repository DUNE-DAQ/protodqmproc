# Overview
This document will draft the requirements for storage and UI for the DAQ

# UI
The UI is the method for which users interface with the DQM data store. It will provide a set of tools to visualise and inspect the store. 

## Users
The UI is expected to provide interfaces for both expert users and non-expert "shifters". We will treat shifters as a subset of experts, with experts requiring all tools provided to shifters. The requirements are thus split:
* Shifters: A navigable UI that can relate stored DQM information to elements of the detector. It must provide easily understandable information regarding component status, current values of DQM information and graphical displays of store queries.
* Experts: The expert interface additional must provide the ability to query the store more generally. Should have capability to make a variety of plots + save these views

## Interfaces
* Visual interface required for both shifters and experts
* Possible additional "intermediate API" between database and UI tools depending on requirements with some tools preferring to directly query databases

## Technologies Considered
* Grafana: Not shifter-friendly but otherwise provides full suite of tools. Navigation more difficult for shifters, somewhat "unfriendly"
* ROOT: Not natively support SQL queries any more
* Python: Requires large initial legwork + maintenance but most customisable setup. Current considered technologies:
    * Sqlalchemy
    * Flask
    * Jinja
    * Bokeh
    * Matplotlib

## Current Design Thoughts
### Visual Elements
* Current required plots
    * 1D timeseries
    * 1D + 2D histograms for metrics
    * "Status" panels displaying the current state of the detector
* Navigation components:
    * Tree view of detector for "overview"
        * Should drive interface design, with initial "splash" page showing status of large-scale detector elements
        * "top bar" to navigate to related queries/objects on the same "level"

### Interface with Storage
* Must be able to do simple database queries
* Provide plot-json? 
* Need to determine maximum time interval queries will be performed over. This will also add an extra constraint on DB technology

# Store
Storage for DQM, stores timestamped metrics. 

* We define measurable entities to be any entity that produces DQM metrics
* We can form natural groupings of measurable entities that we relate to physical hardware in the detector.  

## Technology
* Assumption is SQL database
* Technology not decided. All prototyping has used postgresql
    * Not clear what the read/write speeds required are making final technology decision hard
* Can provide a helper interface/API (see above) to be used in all interactions between store + rest of the DQM
    * Potentially unnecessary as SQL queries are relatively trivial
    * Can look at CCM monitoring (protobuf) for an API design 

## Database Format
* The DQM will use version controlled databases. If table changes are requested, this requires a new database to be created
* The database consists of 3 broad table types:
    * Measurable entity tables
    * Relationship table(s)
    * Alert flag table

* Each measurable entity will have its own table
    * The table columns will be a timestamp and the metrics for that entity
    * Advantages:
        * Smaller tables should lead to faster queries
        * By separating each measurable entity by table, a "entity" ID column is not required
    * Disadvantages
        * Querying over many tables slightly more complex
        * Requires additional relationships table for ORM to work

* Relationships between metrics tables will require an additional table
    * Object relational model (ORM) naturally fits this design
    * Initial building of ORM should use detector maps/similar to automatically map detector elements to their "parents"
    * Detector naturally forms a tree i.e. FD HD -> APA X -> Channel Y 
        *  Will form basis for visualiser design
    * I think should probably be of form [child identifier | parent identifier ] rather than [parent identifier | list of children] as this simplifies merging operations

* The flags table provides a method for storing alert flags generated by the alerts system 
    * Will require id(s) to be recorded for flags
